# Present and the Writer arriving and leaving (#133, #136; app.css "Present
# and the Writer arriving and leaving", openPrompter/closePrompter in
# 20-teleprompter.js, openWriter/closeWriter in 19-writer.js).
#
# Both fade in over the view they cover and back out, on the shared motion
# tokens. What this suite holds them to is what the issues asked for:
#
# - the fade really runs (a CSS transition on opacity, the value mid-way
#   between 0 and 1) and `hidden` still flips in the open/close call itself,
#   so every suite that reads `.hidden` straight after a click is unaffected;
# - nothing the reader or writer needs waits for it: keys, Play, Mirror/Flip
#   and the caret work during the arrival, and a click during the departure
#   lands on the view coming back;
# - closing the Writer saves what is on screen BEFORE anything about leaving
#   happens (a data-loss invariant, not a cosmetic one);
# - Present stops playback and releases the wake lock at once, and when it is
#   fullscreen it holds, opaque, until the browser is out of fullscreen, and
#   only then fades;
# - the side panels a mode closes leave inside the mode's own arrival.
#
# The fades are 180ms/120ms, far too short to sample reliably through a driver
# round trip, so most sections slow them down: __slow(ms) sets --dur-enter and
# --dur-exit inline on #prompter and #writer. The transitions read the tokens
# through var(), so this is exactly the motion the app runs, only longer, and
# nothing outside the two elements is slowed. __fast() takes it back off.
#
# A fade OUT can read its starting value for a frame or two after it starts
# (SKILL.md, "A CSS fade-out reads its starting value..."), so mid-departure
# readings are taken on the page's frames by __mid, never after a bare sleep.
#
# Reduced motion needs nothing here: the tokens collapse to 0.01ms in the one
# @media block 61-transitions.txt already reads back, and these transitions
# are written only in the tokens (checked below).
