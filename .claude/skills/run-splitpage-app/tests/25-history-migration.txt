# =============================================================================
# a key that changes while a migration is already running is never left
# deleted unless its LATEST content is what actually made it into Older —
# the safety invariant behind "not deleted until re-migrated".
#
# The change is made at a moment this test CONTROLS: the migration is parked
# on the 'delay-import' gate, having read the key but not yet confirmed it.
# Racing a bare setItem() against an in-flight migrate() (what this case used
# to do) decides nothing — on a fast idb the migration finishes and deletes
# the key before the next CDP round trip lands, so the "mid-migration" write
# is really a write AFTER the migration and the case then reads a key it

# that made this the suite's load-sensitive failure, not a product bug.
