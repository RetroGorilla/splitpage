# The header's condense/expand as one movement (#52, 20i-topbar.js + app.css)
# and the document keeping step with a side panel that is leaving as well as
# arriving (#53, the #root rules in app.css).
#
# Since #169 (Direction B) the header's own row is one line that never
# changes; what condensing sheds is the rundown strip's time ruler, and the
# strip's track of blocks rises into its place. So where this suite used to
# watch the brand line fade, the toolbar travel and the title scale, it now
# watches the ruler fade (.rundown-ruler) and the track travel
# (.rundown-track), and asserts the title does NOT move. The mechanics under
# test — one frame of layout, a transform putting the pixels back, a
# reversal replacing rather than layering, the thresholds, reduced motion —
# are exactly what they were.
#
# Animation cannot be judged headless — whether the movement READS as one
# thing is a human's call. Its mechanics can be, and that is what this suite
# is: the layout lands in one frame, a transform puts the pixels back, a
# reversal cancels what was running instead of layering a second transform
# over it, and the transitions are the ones the two issues asked for.
#
# Every mid-movement reading is taken in ONE eval into a snapshot object and
# asserted against afterwards. A run of `expect`s straight against the live
# page would each cost a driver round trip, and eight of them after a 60ms
# sleep can walk past the 180ms the movement lasts on a slow machine — the
# assertions would then be timing the harness rather than the app.
#
# The two mid-movement snapshots are also taken on the page's own frames
# rather than after a `sleep`: in the first animation frame after the one the
# class flipped in where the brand line has visibly started to fade. See
# __snapMid below for why a wall-clock sleep cannot promise that.
#
# Two things about how the reduced-motion half is driven, because neither is
# obvious:
#
# - The driver's `viewport` sets device metrics, not media features, so there
#   is no way to ask this browser for prefers-reduced-motion: reduce. The JS
#   half is driven instead by replacing window.matchMedia — 20i-topbar.js
#   calls it at decision time rather than caching the answer, so a stub
#   really does take the no-motion path, and the case below asserts the class
#   still flips with nothing animating and nothing taken out of flow.
# - The CSS half is read off the shipped stylesheet rather than measured: the
#   @media (prefers-reduced-motion: reduce) blocks are found in
#   document.styleSheets and their text asserted. That proves the rules ship
#   and say what they must; it does not prove the browser applies them, which
#   is the browser's job and not this app's.
#
# Everything here is one line per eval — the driver reads the script line by
# line. viewport is set once at the top (>=1100px, where #root's padding-right
# tracks the open panel) and never changed again, and there is no `goto` after
# the first; see the SKILL's gotchas on both aborting the CDP socket.

# __snapMid(name, y) scrolls to y and takes the snapshot mid-movement. That
# moment is defined by the page's frames, not by a `sleep`, because in the
# frame the class flips in the condensing brand line still reads opacity 1,
# and it can go on reading 1 for a frame or more after that:
#
# - The fade out is a CSS transition (.is-condensing in app.css). A transition
#   has its before-change value until the document timeline moves past the
#   frame it began in, and the timeline only moves when a frame is produced.
# - Opacity runs on the compositor, so Chromium holds the transition `pending`
#   (startTime null, currentTime 0) until the compositor reports it started.
#   Traced here: pending in the flip frame every time, and in one trace in
#   six still pending in the frame after it. With the page's frames slowed to
#   ~45ms (a rAF busy-loop), it was still pending one frame after the flip
#   every time. The start time is then backdated
#   to the frame it really started in, so the fade runs its full --dur-exit.
#   It has not been skipped, only started late.
#
# Every other mid-movement reading already holds in the flip frame: the FLIP
# transforms start at their most displaced value, and the fade IN on the way
# back up starts at 0. Only the fade OUT's starting value is the value it
# leaves. `sleep 60` then `__snap` was about 60ms after the scroll, not
# after the flip: the scroll's frame, the rAF-coalesced listener and the
# compositor's start can all come late under a loaded headless browser, and
# when all of that took 60ms or more the snapshot saw `brandOpacity: 1` next
# to `condensing: true`. That is the 61-transitions flake (1 run in 6-8 in the
# cloud container, more often beside other suites). With ~45ms frames it
# failed on exactly that line in 10 runs out of 10.
#
# So: watch the class flip (a MutationObserver on .topbar), then on each later
# frame snapshot as soon as the brand line has left 1. If the movement ends
# first (.is-condensing dropped on the way down, no animation left on the
# toolbar on the way up), the snapshot is taken then, and the assertions below
# fail on it. A fade that never runs still fails this suite, as it should.
eval (function(){window.__snapMid=function(name,y){return new Promise(function(resolve){var t=window.__tb(),want=!t.classList.contains('is-condensed'),flipTl=null,frames=0;var mo=new MutationObserver(function(){if(flipTl===null&&t.classList.contains('is-condensed')===want)flipTl=document.timeline.currentTime;});mo.observe(t,{attributes:true,attributeFilter:['class']});function tick(ts){if(flipTl!==null&&ts>flipTl){frames++;var fading=parseFloat(window.__cs('.rundown-ruler','opacity'))<1;var moving=want?t.classList.contains('is-condensing'):window.__anims('.rundown-track')>0;if(fading||!moving||frames>=60){mo.disconnect();resolve(window.__snap(name)+' ('+frames+' frame(s) after the flip)');return;}}requestAnimationFrame(tick);}requestAnimationFrame(tick);window.__scroll(y);});};return true;})()
expect true
