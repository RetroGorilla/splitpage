# The browser's one-time move of version history from the v1 IndexedDB
# layout into the v2 one (#83, step 3b): 03c-history-idb.js's migrator, run
# as the IndexedDB backend's first job when 03a-history-store.js opens the
# shared store over it. v1 kept every snapshot twice over — a snapMeta row
# and a snapBody row per (docId, id), a docs row per document with byte and
# count counters; v2 keeps one index record per bucket and one body per
# distinct content (bodies are shared by sha).
#
# The v1 database is written raw, exactly as the pre-#83 build laid it out,
# through __historyTest.seedV1 (03c's seedV1HistoryDb) with the page's own
# backend closed and the database deleted first — so the next page load is
# the first thing to open it, the way a real upgrade meets an old profile.
#
#   1. a straight move: every snapshot with a body is readable afterwards
#      (ids, metas, bodies, titles, the Older bucket's 90 days as they were),
#      the one whose body was already lost is dropped, two snapshots with the
#      same content share one body, and the v1 stores are left empty;
#   2. a move stopped after 2 rows (the migrate-stop-after:2 fault, which
#      outlives the reload in sessionStorage): the page still reads
#      everything — moved rows from v2, the rest through the read-only v1
#      reader — while a new capture is kept PENDING in the page with one
#      toast and one panel line naming the unfinished move; then a reload
#      without the fault resumes and ends byte-identical to case 1.
#
# Each goto wipes window, so the spec and case 1's result ride in
# sessionStorage, and every page re-defines its helpers.
