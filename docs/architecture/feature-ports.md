# Connecting moved files: ports and wiring for L5

How a file that leaves `src/js` connects to the rest of the app, for step L5 of [the legacy-reduction plan](legacy-reduction.md). Written on `a1615c0` (`4.1-development`, 2026-10-23), after the first two L5 moves, #730 (script zoom, at `0bd05d6`) and the rundown branch (`claude/project-thread-h2ggei`, at `e98fbae`), connected their files in slightly different ways.

Status: draft for Adam's review. No code changes with it.

The per-file detail (every import, importer and bridge name) is in [feature-ports-inventory.md](feature-ports-inventory.md), generated by the script in the [appendix](#appendix-regenerating-the-inventory).

## In short

- 56 numbered files remain in `src/js` (29,912 lines). 29 of them are still in the import loop, which L3f, L3g and L3h are finishing.
- A move only counts if the moved file stops importing bridges and numbered files (the #730 review). 55 of the 56 files reach at least one bridge, and 43 import an adapter or another feature folder, which a feature may not do either.
- The same connections come up again and again. 43 files reach the session bridge, 30 the location bridge, 29 the notices and 28 the preferences. If every move writes its own port for these, as #730 and the rundown branch do, we get dozens of private copies of "read the document" and "show a notice", each with its own test fakes.
- So the common connections get built once, as **shared ports**, and every move uses them. A move then only has to design the connections that are really its own.
- Not every numbered file is a feature. 16 files (the 15 in Wave 4, and `12a-undo`) are wholly or partly owners or adapters in the wrong folder: document identity, version history, sync and merge, undo, the server client, saving, opening files, file formats, the desktop glue and drafts. Those parts go to `src/application/` or `src/adapters/`, not `src/features/`.
- Order: Wave 0 is the two moves in flight, reworked onto the first shared ports. Waves 1 and 2 are files outside the loop. Wave 3 waits for L3f to L3h to empty the loop. Wave 4 is the owners and adapters.
- Who: 19 files (9,436 lines) are Codex-safe and 36 (20,410 lines) need Opus. `03b-side-panels` (122 lines) is deleted by L3f.

## Words used here

| Word | Meaning |
| --- | --- |
| Numbered file | A file in `src/js/` whose name starts with a number, such as `05-render.js`: the old app code |
| Bridge | A file in `src/legacy/` that hands numbered files an owner through a function call, such as `currentDocument()` or `showToast()`, and throws before the app starts. Bridges exist only for numbered files, and each one goes when its last numbered importer does (plan §8) |
| Owner | The one module that holds a piece of state and is the only way to change it: the document session, the preferences, the save coordinator, the row drag. Owners live in `src/application/` |
| Feature | A folder in `src/features/` for one part of the screen. It may import `src/core/`, `shared/`, `src/application/`, `src/contracts/` and `src/features/common/`. It may not import a bridge, a numbered file, an adapter or another feature (`layerAllows` in `tools/dep-report.mjs`) |
| Port | What a feature needs from outside, written as a TypeScript interface the feature declares. The feature says what it needs and doesn't know who provides it |
| Shared port | A port type several features use, defined once |
| Wiring | The code in `src/bootstrap/wiring/` that builds a feature's ports from the real owners and starts the feature ("mounts" it). Mounting returns a `dispose` function that removes the feature's listeners |
| Action | A named thing the app can do, such as `script-zoom-in` or `go-to-scene`, registered in the action registry (`src/application/actions.ts`) and run from menus, keys, the command menu or code |
| Fake | A small stand-in for a port in a test, such as a notices fake that records messages instead of drawing them |
| Crossing | One import between a moved file and something it may no longer import. Each crossing becomes a shared port, an owner port, an action, a callback or a common helper |

## What the first two moves show

Both move a numbered file into a feature folder, give it a `ports.ts`, and mount it from a new `src/bootstrap/wiring/<name>.ts`.

**Keep:**

1. The feature imports no bridge and no numbered file. Only the wiring reaches the bridges, and the dependency baseline gains nothing.
2. The port interface lives in the feature folder, and the wiring fills it in.
3. The mount returns `dispose`, and the wiring holds it with `owned()` (`src/features/routing/owned.ts`), so mounting again removes the old listeners. The numbered files never removed theirs.
4. The file's start slot in `_entry.js` is replaced at the same position, so the start order the load-order probe checks doesn't change.
5. `tests/features/<name>/mount.test.ts` builds the feature with fakes and no app.

**Change:**

1. **The ports copy the old imports.** #730's 9 fields are the names its 4 imports gave it, one for one, and the rundown's 17 fields are the same for its imports. Both pass how preferences are stored (`isScriptScaleKey`, `isRundownMinKey`, `preferenceEvent`) and still listen to the browser's `storage` event themselves. The rundown also passes a pure helper (`cssAttr`) and two functions from other numbered files (`revealRow` from `01b-hide-shot`, `clearDropMarkers` from `06-rows`) straight through. The plan warns against exactly this in [Why not hand files their imports at startup](legacy-reduction.md#why-not-hand-files-their-imports-at-startup): the link leaves the import graph but the dependency stays, and is harder to follow. Done 55 times it would also give 55 private versions of the same dozen connections.
2. **Numbered files import the moved feature.** In the rundown branch, `05p-rundown-presence`, `05t-target` and `01-scene-status` import `features/rundown/rundown.js`. The layer rules allow it, since a numbered file may import anything, but it turns the feature into a library that old code calls into, and nothing records it.
3. **Actions register two ways.** #730 registers its zoom actions from its wiring. The rundown keeps its action in `legacy/this-document-actions.ts`, to keep its place in the menus, and passes the rundown in. Each is reasonable alone; the pattern needs one way.
4. **`_entry.js` reaches each mount through a re-export added to `bootstrap/wiring.ts`** (`export { __init as initScriptZoom }`), because the frozen-shim test (`tests/bootstrap/legacy-shim.test.ts`) lets the entry import only `wiring.ts` and `app.ts` from bootstrap. That works as the entry's one door, but needs a stated rule so it stays the only re-export.
5. **State and ports sit in module variables** (`var ports = null`). Calling an export before the mount fails on `null`, and a second mount starts from the first one's state. Acceptable for a move ([Rule 1](#rule-1-a-move-keeps-the-files-code)), as long as no other area calls those exports.

**Recommendation:** rework both before they merge. #730 is small, so it becomes the first PR of this pattern and carries the shared-ports builder, the fakes and the action-order test. The rundown rebases onto it as the second. Their behaviour and tests stay; only the port shapes and where the actions register change.

## The pattern

### Rule 1. A move keeps the file's code

A move PR changes how a file is connected, not how it works, so it keeps the diff readable and the behaviour unchanged. A moved file may keep its module variables, but:

- its ports arrive only through its mount (`mount<Name>(ports)`, or `__init(ports)` while that is the file's name for it), and `dispose` removes its listeners and timers and clears the ports;
- every export other than the mount is either a pure helper (no state and no ports; better placed in `src/core/`, `shared/` or `src/features/common/`) or used only by files in the same feature folder and by tests.

Code written new in a feature uses a factory instead: `create<Name>(ports)` returns an object with the feature's methods and `dispose`, and keeps its state inside, as `createSidePanels` does in L3f. Turning a moved 1,000-line file into a factory is its own later PR, not part of the move.

### Rule 2. A port is built from shared ports, owner types and the feature's own needs

A feature's `ports.ts` has three kinds of field:

| Kind | Example | Rule |
| --- | --- | --- |
| Shared port | `document: DocumentReader`, `notices: NoticePort` | Use the type from the [catalog](#the-shared-ports), narrowed with `Pick` to what the feature calls |
| Owner type | `rowDrag: Pick<RowDrag, "dragging" \| "end">` | Use the owner's own interface, narrowed. Never retype an owner's methods by hand |
| The feature's own | `onPainted: (what: Painted) => void` | Named for what the feature needs or tells, not for where the wiring gets it |

A port never carries:

- a pure helper or a constant: the feature imports it from `src/core/`, `shared/` or `src/features/common/`;
- a function of another feature or a numbered file: that becomes an action, an owner or a callback ([Rule 5](#rule-5-features-reach-each-other-four-ways)), or, while that numbered file hasn't moved yet, a field shaped for the need (Rule 5, "Calls into a file that moves later");
- storage keys, DOM event names or `storage` events: those are the owner's business, and the feature hears about changes through the owner's `onChange`;
- a field the feature doesn't use. The typecheck can't catch this, so the reviewer does.

### Rule 3. Where ports live

| What | Where |
| --- | --- |
| A port only one feature uses | `src/features/<name>/ports.ts` |
| A shared port whose owner already has an interface | The owner's own type, imported from where the owner defines it, such as `NoticePort` in `application/effects/ports.ts`, `Preferences` in `application/preferences/preferences.ts`, `ActionRegistry` in `application/actions.ts`, `SidePanels` in `application/side-panels.ts` (L3f) |
| A shared port with no owner interface yet | A new interface beside its owner in `src/application/` |
| Something an adapter provides (the desktop, the picture store) | An interface in `src/application/` shaped for what features need, which the adapter satisfies. A feature may not import even a type from `src/adapters/` |
| Markup and page helpers with no state that two features need | `src/features/common/` |

There is no separate catalog folder. This document's [catalog](#the-shared-ports) is the index, and each entry names where its type lives.

A feature imports from `src/application/` only types and pure functions, such as command builders (`sceneLengthCommand`) and rules. Owners with state, such as `prompter-state.ts`, come in through ports, so a test can fake them.

### Rule 4. How the wiring mounts

- **One wiring module per feature**, `src/bootstrap/wiring/<name>.ts`. It exports `mount<Name>Feature()` and `stop<Name>Feature()`, built on `owned()`, and the feature's action definitions if it has any ([Rule 6](#rule-6-features-own-their-action-definitions-bootstrap-owns-their-order)). It doesn't export `__init` and doesn't re-export the feature's functions.
- **Shared ports are built in one place**, `src/bootstrap/wiring/shared-ports.ts` (new), as `sharedPorts()`. Each shared port object forwards to its owner or bridge at call time, as `appActions` in `legacy/app-actions.ts` already does, so it can be built once and still follows a restart. A feature's wiring takes only the fields its port names.
- **Start position.** A moved file's slot in the `_entry.js` start list is replaced, at the same position, by a call to its wiring's mount. `_entry.js` reaches the mount through one named re-export in `bootstrap/wiring.ts` (`export { mountScriptZoomFeature } from "./wiring/script-zoom.ts"`), because the frozen-shim test allows the entry only `wiring.ts` and `app.ts`. This is the only re-export the pattern allows. A move PR doesn't move the mount into `startApp` (`bootstrap/app.ts`): that would change when the feature starts, which is a behaviour change.
- **Stopping.** Features mounted from the `_entry.js` list are not stopped by `stopApp`, just as the numbered files they replace were not. The last L5 step turns that list into a wiring step, which stops them in reverse order.

### Rule 5. Features reach each other four ways

A feature never imports another feature, and nothing outside its own folder, the wiring and the tests imports it. When one feature needs another, it is one of four things:

| It needs to | Way | Examples |
| --- | --- | --- |
| Make another feature do something | Run that feature's action by id through `actions.invoke(id, source, input)` (the `input` argument arrives with L3g), or use the side-panels port for panels | `go-to-scene`, `annotate-picture` (L3g); `sidePanels.open("comments-panel")` (L3f); the new `reveal-row` |
| Know some state | Read the state's owner through a port. If only a feature holds the state today, it moves to an owner first, as L3b did for area state | rundown minimised: `preferences.rundownMin()`; a person's colour: the presence owner; find open: `viewFlags.findOpen()` |
| React when something happens elsewhere | Subscribe to the owner's announcement, or, when one feature produces the event, give it an output callback (`onPainted`) that the wiring connects to the other feature | the session's change announcements; the render's paint announcements from L3e PR 4 (#714), which the wiring passes on to the panels |
| Use the same markup | A stateless helper in `src/features/common/` | `cssAttr`; the stateless parts of `editableCellHtml` and `slotPoster` |

A quick test: if feature B is about to call `a.something()`, then A does something (an action), A knows something (an owner), or A tells something (a callback).

**Numbered importers during the move.** When a file moves, the numbered files that imported it switch, in the same PR, to the action, owner, callback or common helper above. The one exception is a numbered file that moves into the same feature folder next, such as `05p-rundown-presence` and `05t-target` after the rundown. The PR lists those. The rule enforces itself in the end: when that importer moves, the layer rule fails until the crossing is designed.

**Calls into a file that moves later.** Sometimes the moved code needs an answer from a numbered file that moves in a later wave, and there is no owner or action for it yet. An action can't help when the caller needs a result, since `invoke` returns only whether it ran. In that case the port field is shaped for what the feature needs. It is typed in the feature's `ports.ts` when only that feature needs it, or as the owner-to-be's interface in `src/application/` when several do. The wiring fills it from the numbered file, since bootstrap may import anything. When that file moves, its own move PR gives the field its lasting source (the new owner, or the moved feature's control object), and the feature that uses it doesn't change. The PR lists each such field. This differs from copying the import list: the field is named and typed for the need, not for the file that provides it today.

**Bridges that import the moved file.** A bridge may not import a feature (`layerAllows` lets `src/legacy/` import numbered files but not `src/features/`), so the move PR also settles every bridge import of the file, listed under "Imported by bridges" in the [inventory](feature-ports-inventory.md):

- An action definition that calls the file moves into the feature's `actions.ts` ([Rule 6](#rule-6-features-own-their-action-definitions-bootstrap-owns-their-order)). The legacy actions file keeps its other definitions until their files move.
- State that a bridge reads, such as `tourShowing()` for `legacy/screen-state.ts`, moves to an owner in its own PR first (Rule 8, step 1).
- Anything else goes through a hand-off, below.

**Hand-off bridges.** A few bridges wrap no owner. One numbered file hands its functions in, and other files call them:

- `legacy/tour-pause.ts`: `20c-help` hands in the tour's interrupt and resume, and `20e-connect` calls them around its dialog.
- `handServerCheckTo` in the location bridge: `13-hosted` hands in its server check, and `20e-connect` and `20f-desktop` call it through `checkServer()`.

These are connections between two areas, not shared ports. When the file that hands its functions in moves, its mount returns them as a small control object, typed in its own `ports.ts`, and its wiring hands that object to the bridge. The numbered callers keep working unchanged. When the last caller moves, its call becomes one of the four ways above, usually an output callback the wiring connects, and the hand-off goes (for `tour-pause.ts`, the whole file). Its entries in `src/test/_load-order-hooks.mjs` and `tests/bootstrap/legacy-shim.test.ts` go with it.

### Rule 6. Features own their action definitions; bootstrap owns their order

- A feature's action definitions (id, label, icon, words, keys, availability, run) live in `src/features/<name>/actions.ts`, as a function that takes what the actions control and returns `ActionDefinition[]`. For the rundown that is `rundownActions(rundown: { minimized(): boolean; toggle(): void })`, with the `RundownMinimizer` interface moving from `legacy/this-document-actions.ts` into the feature. Availability uses the screen port ([P6](#the-shared-ports)) and the pure rules from `application/screen.ts`.
- The action registry lists actions in the order they were registered (`list()` reads a `Map`), and the command menu shows that order. So `src/bootstrap/actions.ts` holds the one ordered list, and puts each feature's definitions where they were before. The legacy `register…Actions(registry)` functions become `…Actions(): ActionDefinition[]` as they are touched, so bootstrap can place a feature's definitions between two legacy ones without splitting files.
- A test pins the order: `tests/bootstrap/action-order.test.ts` (new, in Wave 0) checks the registered ids, in order, against today's list. A move that changes the order fails it.
- An action's `run` reaches the feature through its wiring's `owned()` holder. While the feature isn't mounted, the action's availability is `{ enabled: false }`, so the registry refuses it instead of calling into nothing.

### Rule 7. Tests build features with fakes

- Each moved feature gets `tests/features/<name>/mount.test.ts`, which builds the feature with fakes and jsdom (`tests/features/editing/jsdom.mjs`, or `tests/features/view-harness.ts` for the full page) and no app, as `tests/features/script-zoom/mount.test.ts` does. The test runner already requires a test beside every feature folder that holds TypeScript.
- Fakes for the shared ports are written once, in `tests/features/fakes.ts` (new): a document reader holding a given document, notices that record what they were asked to show, preferences in memory that announce changes, an action runner that records what it ran, ids from a counter, a fixed clock. They implement the shared types, so the typecheck keeps them in step with the real ports.
- The app-level tests in `src/test/` keep checking the real wiring end to end. A move changes only their import paths, and the counts in `tests/bootstrap/legacy-shim.test.ts`, never their assertions.

### Rule 8. What a move PR contains

1. Before the move, in its own PR: if other areas read state the file holds, that state moves to an owner (Rule 5). A move PR doesn't create owners.
2. `git mv` of the file to its destination, kept as JavaScript (with its path added to the browser-globals list in `eslint.config.mjs`). Converting it to TypeScript is a separate PR.
3. `ports.ts` built per [Rule 2](#rule-2-a-port-is-built-from-shared-ports-owner-types-and-the-features-own-needs), using shared ports that exist, or adding the ones it is the first user of ([catalog](#the-shared-ports)).
4. The wiring module, the `_entry.js` slot and the action definitions per Rules 4 and 6.
5. Every numbered importer switched per [Rule 5](#rule-5-features-reach-each-other-four-ways), or listed as moving into the same feature next.
6. `tests/features/<name>/mount.test.ts`, plus fakes for any new shared port.
7. `tools/dep-baseline.json`: the file's `legacy-file`, `loop-import` and `cycle-edge` entries pruned; nothing added.
8. The "Structure" section: which responsibility moves where, which bridges and numbered files the moved code no longer imports, and the `--legacy-metrics` figures before and after.
9. Gates: lint, types, `check:deps`, `check:comments` and the file's tests; one perf-ab run if the file is on the typing path (Adam's lighter rule of 2026-10-23); the desktop smoke if it calls the desktop port.

**Opus or Codex.** A move is Opus when the moved code *does* one of: run on the typing path, record or replay undo, save, recover or keep drafts, bring a document in (open, import, paste, merge, server, starters), talk to the preload bridge, or handle close and quit. A move is Codex-safe when the code only *calls* those through a port that has already landed, unchanged. The PR lists each such call so the reviewer, who is Opus anyway, can check it.

Why this order:

- Wave 0 settles the pattern on two moves already written, and between them lands the shared ports most files need (P1, P3 to P6, P8, P10).
- Waves 1 and 2 are outside the loop, so they can run while L3f to L3h finish. Wave 1 goes first because its files have few crossings; Wave 2 holds the editing files that need P9 to P13.
- Wave 3 waits for the loop to empty: until L3f to L3h merge, those files import each other both ways, and moving one would mean designing crossings those steps are already removing.
- Wave 4 is last because the lifecycle files are owners, not features, and the bridges for them retire with them.
- Within a wave, moves that touch the same files queue behind each other ("one open PR per shared file", as in the plan). The rows, tags and render moves all touch `05-render`'s importers, so they run one after another.

[legacy-reduction.md](legacy-reduction.md)'s L5 section says the remaining files are "feature code in the wrong folder" that move "when a 4.1 feature next changes" them. With this document:

- L5 becomes scheduled work in five waves (0 to 4), not left to feature work. The plan leaves that choice to Adam, so this is a proposal.
- 16 of the files go, wholly or partly, to `src/application/` or `src/adapters/`, not `src/features/`.
- The bridges retire move by move: each bridge's last numbered importer is in the inventory, and its bridge goes in the same PR.
- The Wave 0 PRs add three files outside `src/js`: `src/bootstrap/wiring/shared-ports.ts`, `tests/features/fakes.ts` and `tests/bootstrap/action-order.test.ts`.

## Appendix: regenerating the inventory

The script is not committed, since nothing runs it routinely. To refresh the inventory on a later base, save it as `l5-inventory.mjs` in the repository root, run `node l5-inventory.mjs > docs/architecture/feature-ports-inventory.md`, and delete the script. It reads the import graph through `tools/dep-report.mjs`, the same one `check:deps` uses.

```js
import { execSync } from "node:child_process";
import { loadGraph, stronglyConnected } from "./tools/dep-report.mjs";
const modules = loadGraph();
const numbered = (p) => /^src\/js\/[0-9]/.test(p);
const short = (p) => p.replace(/^src\/js\//, "").replace(/^src\//, "").replace(/\.(js|ts)$/, "");
const loop = new Set(stronglyConnected(modules, false).filter((c) => c.length > 1).flat());
const group = (p) => numbered(p) ? "numbered" : p.startsWith("src/legacy/") ? "bridges" : p.startsWith("src/adapters/") ? "adapters"
  : p.startsWith("src/features/") ? "features" : p.startsWith("src/js/") ? "other src/js" : p.startsWith("src/bootstrap/") ? "bootstrap"
  : /^(src\/test|tests)\//.test(p) ? "tests" : p.startsWith("tools/") ? "tools" : null;
const list = (m) => Object.entries(m).map(([t, n]) => `\`${short(t)}\` (${[...n].sort().join(", ")})`).join("; ");
const rows = [];
for (const p of [...modules.keys()].filter(numbered).sort()) {
  const m = modules.get(p);
  const out = {}, inn = {};
  for (const e of m.edges) {
    if (e.kind !== "file") continue;
    const g = group(e.target);
    if (!g || g === "bootstrap" || g === "tests" || g === "tools") continue;
    ((out[g] ??= {})[e.target] ??= new Set());
    for (const n of e.names ?? []) out[g][e.target].add(n);
  }
  for (const [q, mm] of modules) for (const e of mm.edges) {
    if (e.kind !== "file" || e.target !== p) continue;
    if (q === "src/js/_entry.js" && (e.names ?? []).every((n) => n === "__init")) continue;
    const g = group(q);
    if (!g || g === "adapters") continue;
    ((inn[g] ??= {})[q] ??= new Set());
    for (const n of e.names ?? []) inn[g][q].add(n);
  }
  rows.push({ p, lines: m.text.split("\n").length, loop: loop.has(p), out, inn });
}
const base = execSync("git rev-parse --short HEAD").toString().trim();
console.log(`# Numbered files: imports, importers and bridges\n\nGenerated on \`${base}\` by the script in [feature-ports.md](feature-ports.md#appendix-regenerating-the-inventory). It lists, for each file left in \`src/js\`, what it imports from numbered files, bridges, adapters and feature folders, and who imports it. Imports from \`src/core\`, \`shared\` and \`src/application\` are left out, since a feature may import those. \`_entry.js\` calling a file\'s \`__init\` is left out too.\n`);
console.log("| File | Lines | In the loop | Numbered files it imports | Bridges it reaches | Adapters and features it imports | Imported by |");
console.log("| --- | --- | --- | --- | --- | --- | --- |");
for (const r of rows) {
  const n = (g) => Object.keys(r.out[g] ?? {}).length;
  const by = ["numbered", "bridges", "bootstrap", "other src/js", "tests", "tools"].filter((g) => r.inn[g]).map((g) => `${Object.keys(r.inn[g]).length} ${g === "bootstrap" ? "wiring" : g}`).join(", ");
  const bridges = Object.keys(r.out.bridges ?? {}).map((t) => short(t).replace(/^legacy\//, "")).sort().join(", ");
  console.log(`| \`${short(r.p)}\` | ${r.lines} | ${r.loop ? "yes" : ""} | ${n("numbered") + n("other src/js")} | ${bridges || "none"} | ${n("adapters") + n("features")} | ${by} |`);
}
for (const r of rows) {
  console.log(`\n### \`${short(r.p)}\`\n\n${r.lines} lines${r.loop ? ", in the import loop" : ""}.\n`);
  for (const [g, label] of [["numbered", "Imports from numbered files"], ["other src/js", "Imports from other `src/js` files"], ["bridges", "Reaches through bridges"], ["adapters", "Imports from adapters (a feature may not)"], ["features", "Imports from feature folders (a feature may not import another feature)"]]) {
    if (r.out[g]) console.log(`- ${label}: ${list(r.out[g])}`);
  }
  for (const [g, label] of [["numbered", "Imported by numbered files"], ["other src/js", "Imported by other `src/js` files"], ["bridges", "Imported by bridges"], ["bootstrap", "Imported by the wiring"]]) {
    if (r.inn[g]) console.log(`- ${label}: ${list(r.inn[g])}`);
  }
  const t = Object.keys(r.inn.tests ?? {}).length, k = Object.keys(r.inn.tools ?? {}).length;
  if (t || k) console.log(`- Imported by tests: ${t} file${t === 1 ? "" : "s"}${k ? `; by tools: ${k} file${k === 1 ? "" : "s"}` : ""}`);
}
```
