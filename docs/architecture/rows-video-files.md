# Session video files after the rows extraction

The former `06-rows.js` module is retired. Its remaining video-file responsibilities live in `src/features/gallery/video-files.ts`, with the shared `VideoFiles` contract in `src/application/media/video-files.ts`. The existing beat operations, beat media, row routing and row editing already have their own owners.

## Ownership and wiring

Bootstrap creates the video-file owner explicitly through `mountVideoFilesFeature()` at the old `init_06_rows()` position, after gallery mounting and before beat mounting. Importing the feature, contract or wiring starts no owner and registers no listener. The forwarding `videoFiles` port follows the current owner and throws before mounting or after stopping. There is no compatibility export from the retired numbered file and no new legacy bridge.

The owner receives the existing document reader, notices, desktop-video and external-link ports. It imports only core helpers for row lookup, link normalization, keys and URL safety. Editor/media wiring grants dropped or pasted files through `videoFiles.grant`; the gallery overlay reads `has` and `url`; picture-link actions receive `openGallery` explicitly instead of importing a numbered module.

| Former export | Owner operation |
| --- | --- |
| `grantVideoFile` | `grant` |
| `hasSessionVideo` | `has` |
| `sessionVideoUrl` | `url` |
| `releaseSessionVideoUrls` | `releaseUrls` |
| `openVideoFile` | `openFile` |
| `openGalleryLink` | `openGallery` |

## Lifetimes and preserved behavior

File grants and opaque desktop tokens last for the page owner's lifetime, across document replacement and application-session rewiring. Replacing a document revokes cached object URLs but keeps the grants, preserving the existing lifecycle tests. URLs are created lazily; granting the same file keeps its URL, and replacing that file revokes its old URL.

The new explicit owner's disposal unsubscribes its document listener, releases cached URLs and file/token references, and prevents delayed grant/open completions from operating on a disposed owner. Remounting builds a separate owner; disposing the old instance cannot change its replacement. Normal opening, warnings, capability checks, token forwarding and HTTP(S)-only browser links are preserved. Tokens are never added to document data or exports.

## Stored paths (#259)

A video file dropped in the desktop app keeps its path on its link, so it opens again after a restart. The path comes from the preload's `webUtils.getPathForFile` (`videoFilePath` on the bridge, `pathOf` on `DesktopVideo`), and `readClipboardFiles` puts it on the attachment. The link stores it as `location: { kind: "path", path }`; the browser build has no path and stores none. The other kind, `bundled`, is described in the next section.

Opening a file link tries this session's token first, then the stored path through `openPath` (`splitpage:video-path-open`). A drop grants its file under the link's name and size and, when it has a path, under that path too (`locatedVideoKey`). A link with a path only uses a token, file or preview granted from that same path, so another script's same-named file elsewhere, or a link put back to an older path by undo, opens from its own stored path. A link without a path keeps matching by name and size, as before. A script is untrusted input, so main checks the path itself before anything touches the disk, with `videoPathProblem` in `shared/video-path.ts`: a local drive path on Windows or an absolute path elsewhere, no UNC or device path, no `.` or `..` part, no character or name Windows would reinterpret, and a video extension from the same allowlist as a grant. `openableVideoPath` in `shared/video-embed.ts` then resolves links with `realpath`, checks the extension again on the real path, and requires a regular file. A file that is gone answers `GONE`, which gives the existing "no longer where it was" notice; anything refused answers `REFUSED`, which gives the existing "Could not open" notice.

The core normalizer keeps a location only on a file link and only when it is a valid path in either style, so a script moved between Windows and macOS keeps it. The location is not part of a link's identity (`videoLinkKey`): dropping the same file again records its new path on the link it already has, together with that drop's first frame and length when it could read them, in one edit. The gallery's player is identified by the link and its path (`locatedVideoKey`), so a change of path, such as an undo, replaces a playing video with the still. It is part of the gallery fields' equality key, so a change of location alone is merged and undone like any other gallery change. SplitShare drops every location; the other exports never wrote a link's fields beyond its name.

## Copies beside the script (#259)

When a video with a path is dropped or pasted onto a beat of a script saved on disk in the desktop app, `src/features/gallery/video-bundles.ts` asks whether to copy it into the script's folder; Copy it is the default button. The folder is `<script name without its extension> files` beside the script (the name rules, `bundledNameProblem` and `bundleFolderName`, are in `shared/video-path.ts`, which core can import; the disk rules, `bundleFolderOf` and `resolveBundledFile`, are in `shared/video-embed.ts` beside `openableVideoPath`, which main already loads; both take the allowed extensions as an argument where they check one, so they hold for any file type). A copied link stores `location: { kind: "bundled", name }`, a single file name in that folder, so the script and its folder can move together. Declining, an unsaved script, the browser build, or a failed copy keeps `{ kind: "path" }`, with a notice when the copy failed or was stopped. Photos are not asked about.

The copy runs in main (`desktop/bundle-copy.ts`) as a stream, with progress on `splitpage:bundle-progress` and Cancel on `splitpage:bundle-cancel`; the page stays usable. Main owns the queue (`desktop/bundle-jobs.ts`): accepting the prompt sends every copy at once, and main runs them one at a time. The renderer never names a file to copy or a folder to copy into. `splitpage:bundle-file` takes the drop's grant token (#1250) and copies only that file: main resolves it with `realpath` and checks the extension again on the real file, so a granted name that is a link to something else is refused, and it copies only into the bundle folder of the script the tab had when the copy was accepted. A queued copy is never pointed at another script later: if the tab has opened an unrelated script by the time it starts, main drops it (`DROPPED`, no notice) and the link keeps its path. A name already in the folder gets a number, `take (2).mp4`; a file there is reused only when its size and, compared as a stream, its bytes match, and nothing is overwritten. Every copy, and every file a carry writes, is written to `~splitpage-<16 hex>.part` in the destination folder and published under its own name only when it is whole, so the final name never holds part of a file and nothing is created under it beforehand. Publishing is a hard link from the temporary, which never replaces a file. Where hard links are not supported (exFAT, SMB shares such as a NAS), main checks that the final name is still free and renames the temporary to it; the only race left is another program creating that same name in that instant, which is accepted. Every publish takes a per-folder publish lock for the check-and-publish step only, so a stalled read never holds it. Inside the lock a job checks that it was not cancelled after taking the lock and again after every step before the link or rename; a cancelled job deletes its temporary and publishes nothing, so a job let go after Cancel can never replace a file a later carry published. A temporary older than the current job, left by a copy that never finished (a crash, or the app killed), is removed by the next copy or carry into that folder; a newer one is left alone. Cancel stops every copy of that tab's drops and a carry it is showing, and removes its temporary. Jobs are keyed by the sender, so one tab cannot cancel another's. When the copy lands, the link change folds into the drop's own undo entry when that is still the last one, so one undo removes the drop; otherwise it is its own gallery edit. Undo never deletes the copied file.

`splitpage:bundled-file-open` takes a name, and main resolves it with `resolveBundledFile`: the name rules (no separator, `..`, drive, stream, control character, reserved device name or trailing dot), the video allowlist, a bundle folder that is a real directory rather than a link or junction, a `realpath` whose folder is that bundle folder, and a regular file. Anything else is `REFUSED` or `GONE`, as for a stored path. The core normalizer keeps a bundled location only when its name passes the same rules.

No copy is in flight across a Save As or Save a copy. Before it captures the bytes to write, `file-saving.ts` opens a save window on the gallery (`beginSave`): the save waits until every copy this page sent has answered, behind the same progress panel and its Cancel. Each answer relinks the drop as usual, so the captured bytes already link the copies that landed. Cancel ends the wait at once, even for a copy that never answers (a read stalled on a lost network drive), and abandons that Save As before the capture, the dialog or the retarget, so nothing is written. A late answer for a cancelled copy relinks only while no save is running and the document still belongs to the same script; otherwise the link stays a path. Main lets go of a running job as soon as it is cancelled, so later copies and carries are not held behind it, and an aborted job publishes nothing. While the save window is open, until the save commits or rolls back, a dropped video or attached file is linked by its path with no copy prompt, and an open prompt closes as if declined; dropping it again afterwards asks. Every queued copy stays bound to the script it was accepted for and only ever writes into that script's folder.

The script save dialog asks with `script: true`; main notes the tab and its script when the dialog is answered. After the pick and before anything is written, a Save As or Save a copy whose bytes link bundled files asks "Save the files with this script?" (`ask` in `video-bundles.ts`, called from `writeCaptured`). It reads the bundled names from the bytes it is about to write (`bundledNamesInProject`: the `.splitpage` JSON, or the last `~~~splitpage` block of a `.md`) and sends only them with the file id on `splitpage:bundle-save-plan`. Main resolves each one in the old folder and answers with folder names, the count, the total size, the size not already in the new folder (a file there with the same name and size is not counted), the count with no file in the old folder, and whether every old file could be linked by path. A file in the new folder with the same name and a different size refuses the plan with the clash message below, before the prompt and the write. The prompt says "This script links 2 files in “Episode 12 files” (1.8 GB). Copy files adds them to “Episode 12 v2 files”, next to the new script. Otherwise the new script links to the files where they are now.", with Copy files (the default, showing the size), Don't copy the files, and Cancel; above 250 MB to copy (`BUNDLE_WARN_BYTES`) it adds "That is a lot to copy, and it may take a while and use disk space. You can keep working while it copies.". Cancel abandons the save before anything is written. A script that links no bundled file, plain Save and autosave never ask. The answer goes to main on `splitpage:bundle-save-choice` as `copy` or `link`.

For Copy files, main carries the files along, without the renderer, as one job in the same queue. When that file's first write arrives, main reads the bundled names again from the bytes it is about to write, resolves each one in the old folder with `resolveBundledFile`, and carries only those. A file in the old folder that the written script does not link, such as a drop that was undone after its copy, is never carried. The carry job first compares each of those names with the new folder, byte for byte when the size matches; if the new folder already holds a file of that name with different bytes, the save fails before anything is copied or written, with "“Episode 12 v2 files” already has a different “take.mp4”. Rename or move that file, then save again.". The reason is `bundleRefused` in the write result, and the renderer's save fails with it. Same bytes are no conflict. Then the script is written, and the job copies the rest in the background behind the progress panel; Hide tucks the panel into a chip at the bottom right, "Copying files — 40%", which brings it back. Until a file lands in the new folder, opening one of the names that job lists from that tab's new script opens it from the old folder; that fallback lives in main, is keyed by the tab and the new script, and ends with the job. If a file cannot be copied, or the copy is cancelled, a notice stays until dismissed: "Could not copy “b.mp4” to “Episode 12 v2 files”. 1 file was not copied, so it does not open from this copy of the script. Look for it in “Episode 12 files”." (or "Stopped copying files to …" for Cancel). Files already copied stay, and nothing is deleted. In-place saves of the new script go on during the copy and start nothing. A second Save As waits behind the panel until the copy finishes or is cancelled, and because carries run one at a time in the queue it checks its own folder against what the first left. The carry runs even if the tab or its renderer is gone, and reports on `splitpage:bundle-carry` with folder names and counts only. Exports, other dialogs, file ids no script dialog chose, and later writes to the same file start nothing. A linked name with no file in the old folder is counted in a notice that names the old folder; the link stays bundled, so it opens as `GONE` from the new script.

For Don't copy the files, main rewrites the bytes it writes: each bundled name it finds in the old folder becomes `{ kind: "path" }` to that file, and a name it cannot find stays bundled. Every stored path must pass `openableVideoPath`; a file on a network share cannot, so the prompt turns Don't copy off with "“Don't copy the files” is not available: the files are on a network share, which a script cannot link to.", and a write that still asks for it is refused. The renderer never sees those paths: main remembers them for that script for the session, rewrites its later in-place saves the same way, and opens those names from them, and a later copy into the new folder never takes one of those names. A draft restored after a crash still holds the bundled names, so they open as `GONE`.

A video dropped while a save window or a Save As copy is running is linked by its path with no copy prompt.

Quitting, or closing the last window, while copies or carries are running, including a Save As copy whose tab has closed, asks first: "Splitpage is still copying files.", with Wait (the default) and Quit anyway. Wait lets the queue finish and then quits or closes; Quit anyway stops every copy, removes their temporaries, and then quits. `will-quit` stops anything still running as a last resort.

## Attached files (#256)

The empty beat's button is **Attach**, and its file chooser (also behind the gallery's Add) takes any file; Replace still asks for a picture. A picture is embedded as before. A video takes the video route above. Any other file is attached: `readClipboardFiles` makes it a `file` attachment with its name, size and, in the desktop app, its path, and grants it like a video; `addGalleryFile` (`src/core/document/gallery.ts`) puts its link, `{ name, size, location? }` with no `poster`, on the beat's first gallery item, or on an item of its own with no picture when the beat has none. A beat whose only item is such a link shows the links under its Attach button instead of a picture tile. File links belong to the beat, not to a gallery item: they are stored only in the row's `imageLinks`, which the merge treats link by link, three-way against the base, so a file removed on either side stays removed and one added on either side stays added. `setRowSlots` writes every file link it is given into `imageLinks` and none into `moreImages`, so moving, replacing or removing a picture or video never moves or drops a file, and `rowSlots` shows them on the first item. Normalization moves any file link it finds on a `moreImages` item into `imageLinks`. The 20-link limit applies only when attaching; normalization and merge never drop a file link to keep it. Each line shows the file's type (`videoHostLabel`: PDF, Document, Audio, Sheet, Slides, Text, Image, Archive, else File), a file icon and its name; a click opens it through `openGallery` as for a video file. The copy prompt and its notices say "file" unless every file is a video. In the browser build the link keeps only its name, as a video file's does.

`ATTACHABLE_FILE` in `shared/video-path.ts` is the one rule for what may be attached: a name with an extension that is not on `BLOCKED_FILE_TYPES` (programs, scripts, shortcuts, installers, disk images and the like; trailing dots and spaces are ignored when matching). The renderer uses it to refuse a drop or paste with a notice, the core normalizer to keep a `path` or `bundled` location, and main, which reaches it through `shared/video-embed.ts`, on every video-file channel in place of the video allowlist: a grant (on the dropped path and its real path), a token open (the real path again), a stored path (`openableVideoPath`), a copy, a carry and a bundled open. Exports call such a link "(file)" rather than "(video file)", and still write no location.

The `open-picture-link` action retains its ID, registration position, availability and input validation. The build entry stays `_entry.js`; only its retired initializer is replaced by the explicit feature mount.
