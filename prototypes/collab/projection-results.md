## Mechanisms and departures from artifact 8

- A uses the exported SchemaReplica's document with one flow Y.Text and boundary embeds. B uses segments with head fields and one order array. Both use separate visual components, gallery slots, comment/reply maps and ranked registries. No file in the other lane was changed.
- Both preserve import key order in record keys arrays. This is required by the JSON serializer's byte contract; these arrays contain names, never duplicate field values. Unknown data lives only in each record's extra JSON.
- Legacy rev, lastEditedAt, lastEditedBy and personColors live in meta.capture. The proposed absence/export regeneration and deriving personColors from people cannot reproduce a historical capture. This is import/export evidence, not a shared edit-stamp policy.
- Comment updatedAt is retained; deriving it from replies cannot reproduce an assignment or reopening timestamp without a change history. Comments keep load rowId/field as fallback; concurrent detachment remains for PR 2.
- Comment bodies/replies are atomic sanitized HTML, as the shared-layer write-once body contract specifies. Resolution is one atomic group. Reply keys include commentId to avoid cross-comment id collisions; import rank retains file order rather than sorting existing replies by time.
- Gallery picture data is one coupled JSON value (imageRef, name, annotation); slot identity is minted from origin row and import index, never from content. Links are keyed by the existing href/name/size key. Location stays device-local and is excluded from Yjs; a Yjs-only transfer cannot carry it. Blob bytes also remain external; the reference serializer reuses the fixture blobs, and encoded Yjs sizes exclude them.
- B-roll embeds retain a label in addition to k because the format accepts marker spelling/case variants. Who embeds retain w. Text attributes use one c:commentId, t:occurrenceId and l:occurrenceId per mark; tag registry ids resolve back to names on export. Rich-text decoding is a bounded prototype parser for already-sanitized app documents, not a replacement sanitizer.
- No joins, soft removals, structural recovery or conflicting status semantics are claimed by this full-document layout. Existing trace lanes own those mechanisms. Props remain atomic JSON here; merged-set behavior is not implemented.

## Fixture selection

The two immutable v0.3.0 files exercise actual historical on-disk input. Seed plus all starters include the long demo, script formatting, tags, galleries, comments and production lists used by exports-golden. Every complete document under merge goldens exercises input/base/mine/theirs and expected output states, including conflict cards, stamps, ids, ordering, gallery links and sections. Every migrate-golden output exercises the app's already-normalized shapes, including images, annotations and unknown keys. Non-document arrays and hash-only export summaries are not mistaken for full documents.

The one added fixture, test/proj/supplement.splitpage, covers gaps in that corpus: who-anchor, stored paragraph flags, path/bundled locations, hash-only body images and unknown keys on each of the six nested record kinds. Existing fixtures already cover unknown top-level data, full image references and pen/text annotations; those were not duplicated in the supplement. The local-location loss is asserted as literal before-values with no after-value. The supplement is not silently normalized to become byte-identical.

The app reference runs the existing parseSplitpageFile, migrateRows and buildSplitpageFile in one separate Node subprocess with the repository's DOM shim. It never boots the app, starts a server or runs an app suite. This is an explicit reference-only harness dependency on app codecs outside the permitted prototype import graph; the layouts themselves import only prototype, core and shared modules. Both original and projected saves pass through the same serializer and blob store, after source blobs have been interned. No expected content is derived from the projection.
